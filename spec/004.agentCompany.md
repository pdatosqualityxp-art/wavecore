# Especificación: 004 - Asistente de empresa

## 1. Objetivo

Crear una interfaz de chat para que el usuario pueda escribir una pregunta y recibir una respuesta de un agente conectado a una API. La experiencia debe ser familiar, similar a un chat de asistencia: conversación visible, área para escribir, envío de mensajes y respuesta del agente dentro de la misma conversación.

La integración se realiza con la API REST corporativa documentada en la sección 6. La interfaz envía una pregunta por petición y muestra la respuesta completa, recibida como JSON.

## 2. Alcance funcional

- Permitir al usuario redactar y enviar preguntas al agente.
- Mostrar las preguntas del usuario y las respuestas del agente en orden cronológico.
- Publicar la página en `/agent-company`, con la etiqueta de menú **Consulta de empresa**, inmediatamente después de **Dashboard Ventas**.
- Mantener el código propio de esta funcionalidad dentro de `src/features/agent_company/`.
- Indicar cuándo el agente está procesando una pregunta.
- Mostrar errores de envío o respuesta de forma comprensible y permitir reintentar cuando sea seguro.
- Conectar la interfaz a la API acordada; no usar respuestas ficticias en producción.
- No incluir en esta primera versión gestión de conversaciones, adjuntos, voz ni acciones de escritura sobre datos de la empresa.
- El asistente responde consultas del ámbito corporativo y puede rechazar educadamente preguntas ajenas a la empresa.

## 3. Interfaz de chat

- Mostrar un encabezado con el nombre del asistente y una breve descripción, ambos localizados.
- Reservar la mayor parte de la pantalla para el historial de la conversación.
- Cuando no haya mensajes, mostrar un estado inicial que invite a escribir una pregunta; no presentar sugerencias de preguntas hasta que se definan con el negocio.
- Mostrar cada mensaje en una burbuja o bloque distinguible por rol:
  - **Usuario:** pregunta enviada.
  - **Agente:** respuesta recibida.
- Mantener el orden cronológico y la legibilidad de respuestas largas. El texto de respuesta debe poder mostrar saltos de línea y, si la API lo requiere, formato Markdown seguro.
- Situar al pie un área de escritura con etiqueta accesible, botón de envío y soporte para teclado. El botón de envío debe indicar claramente que envía la pregunta.
- Enviar con Enter y permitir un salto de línea con Shift+Enter, si este comportamiento puede implementarse de forma accesible y se documenta en la ayuda del campo.
- Deshabilitar el envío cuando la pregunta esté vacía o sólo contenga espacios, o mientras haya una petición activa si la API no admite solicitudes concurrentes.
- Limpiar el campo después de aceptar el envío y conservar el texto si la petición falla de forma que permita reintentar.
- Mantener el último mensaje visible al recibir una respuesta, sin impedir que el usuario consulte mensajes anteriores.
- En móvil, mantener el campo y el botón accesibles con el teclado virtual abierto y evitar desbordamiento horizontal.

## 4. Flujo de conversación

1. El usuario escribe una pregunta.
2. Al enviarla, la interfaz la añade al historial y muestra el estado de procesamiento del agente.
3. La aplicación envía la pregunta y, si corresponde, el contexto de conversación a la API.
4. Al recibir una respuesta válida, la añade al historial con el rol del agente y retira el indicador de procesamiento.
5. Si la petición falla, informa del error, conserva el historial existente y ofrece reintentar sólo en los casos transitorios definidos en la sección 6.

La API es stateless respecto al contexto conversacional: cada solicitud incluye una sola pregunta y el servidor obtiene de nuevo el contexto corporativo actual. El historial que aparece en pantalla es sólo local a la vista y no debe enviarse como historial conversacional ni presentarse como memoria del agente. Evitar envíos duplicados accidentales.

## 5. Estados y errores

- **Inicial / conversación vacía:** texto localizado que explica que se puede hacer una pregunta.
- **Envío y espera:** indicador accesible de que el agente está respondiendo; el control de envío refleja si se permiten más preguntas.
- **Respuesta recibida:** mostrar el contenido proporcionado por la API y restablecer el estado de espera.
- **Error de red o del servidor:** mostrar un mensaje localizado y una acción de reintento cuando sea seguro. No borrar la pregunta ni el historial.
- **Respuesta vacía o inválida:** informar que no se pudo obtener una respuesta válida; no mostrar una respuesta inventada.
- **Error HTTP 400:** mostrar un mensaje localizado de pregunta no válida; no reintentar automáticamente.
- **Error HTTP 500 o fallo transitorio de red:** mostrar un mensaje localizado. Permitir como máximo dos intentos totales ante fallos puntuales de red, con espera exponencial; no reintentar automáticamente respuestas HTTP recibidas.
- **Timeout:** la petición puede tardar hasta el límite de la Serverless Function de Vercel (según plan, aproximadamente 10–60 segundos). Si se agota el timeout, explicar que no se recibió respuesta y permitir un reintento manual.

Los detalles técnicos recibidos de la API no deben exponerse directamente al usuario. No mostrar ni registrar en logs del frontend el `clientIp`, detalles internos del servidor ni otros datos técnicos. Los reintentos de POST pueden volver a generar costes de modelo y, cuando la auditoría esté implementada, filas de registro; por eso limitar los intentos y no hacer reintentos automáticos tras una respuesta HTTP recibida.

## 6. Integración con la API

- Encapsular las llamadas en un servicio de la feature, separado de los componentes visuales.
- **Ruta desde el frontend:** `POST /api/chat` en el mismo origen. La configuración de Vercel reenvía esa ruta a `https://wavecore-api-company.vercel.app/api/chat`; el navegador no realiza una petición cross-origin.
- **Frontend local:** Vite reenvía `/api/*` a la API desplegada por defecto.
- **Backend local opcional:** `http://localhost:3000`, configurable como destino del proxy local mediante `VITE_AGENT_COMPANY_API_URL`.
- **Comprobación de estado/bienvenida:** `GET /`.
- **Chat:** `POST /api/chat`.
- Obtener la sesión vigente con `supabase.auth.getSession()` antes de cada petición. Si no hay un `access_token` válido, no enviar la pregunta y mostrar un error de sesión.
- Enviar `Content-Type: application/json`, `Authorization: Bearer <access_token>` y el cuerpo `{"message":"<pregunta>"}`. No enviar historial ni credenciales del proveedor.
- El backend valida el bearer token y crea un cliente Supabase exclusivo para esa petición: usar la clave pública/anon como `apikey` y el token del usuario como `Authorization`. No usar `service_role` ni mutar credenciales en un cliente Supabase compartido. Las consultas deben respetar RLS para usuarios registrados y sesiones anónimas.
- Si falta el bearer o no es válido/ha caducado, responder con HTTP 401 y un error de autenticación explícito. No tratar un fallo de autenticación o de consulta como tablas vacías; los errores de Supabase deben impedir que se presente un contexto incompleto como válido.
- La API es una pasarela Node.js/Express a Gemini y Supabase. Las credenciales de Gemini y la clave pública de Supabase se mantienen en el servidor y nunca deben incluirse en el código cliente ni en variables `VITE_*`.
- La respuesta es JSON completa y sin streaming. En HTTP 200, validar `success === true` y que `reply` sea una cadena no vacía antes de mostrarla. `apiVersion`, `modelUsed`, `tokens`, `databaseStatus`, `receivedAt` y `clientIp` son metadatos: no son parte del texto de respuesta, y no es necesario mostrarlos en la UI.
- En HTTP 400 puede recibirse `{"error":"Falta el campo message en el body"}`. En HTTP 500 puede recibirse `{"success":false,"apiVersion":"v1.1","error":"Error interno al procesar la petición","details":"..."}`. Tratar como no confiable el campo `details`; no mostrarlo al usuario.
- La API construye en cada petición un contexto actualizado consultando las tablas corporativas, entre ellas clientes, productos, stock, ventas, compras e intervenciones. La interfaz no debe asumir una conversación persistente en el servidor.
- El backend puede tener previsto registrar las interacciones en `chat_logs`, pero esa tabla aún no existe en Supabase. El registro/auditoría persistente queda fuera de esta implementación y se revisará más adelante; no asumir que las peticiones se guardan correctamente ni mostrar en la interfaz una afirmación de que ya existe ese registro.
- El servidor usa Gemini `gemini-3.1-flash-lite`, con temperatura `0.2` y un máximo de 500 tokens de salida. La UI debe admitir respuestas concisas y no asumir una respuesta larga.
- Usar timeout compatible con el límite del backend de Vercel (10–60 segundos, según plan). Ante fallos transitorios de red, permitir como máximo dos intentos totales con espera exponencial; no reintentar automáticamente errores HTTP ni respuestas 400/500 recibidas. Permitir reintento manual tras fallo, advirtiendo que una repetición puede procesarse nuevamente.
- Validar la forma de la respuesta antes de incorporarla al historial y tratar la respuesta como texto no confiable.

## 7. Diseño, accesibilidad e internacionalización

- Registrar `/agent-company` como ruta hija autenticada dentro del `AppShell`.
- Añadir **Consulta de empresa** a la navegación inmediatamente después de **Dashboard Ventas** y antes de la siguiente sección del menú. El enlace debe seguir los estados activo, plegado y móvil ya existentes.
- Usar el título **Asistente virtual corporativo** en la cabecera de la página y **Consulta de empresa** como etiqueta de navegación; ambos textos deben localizarse.
- Organizar la feature con esta estructura inicial:

  ```text
  src/features/agent_company/
  ├── AgentCompany.tsx
  ├── AgentCompany.test.tsx
  ├── agentCompanyApi.ts
  └── agentCompanyApi.test.ts
  ```

  `AgentCompany.tsx` contiene la página y el estado visual del chat. `agentCompanyApi.ts` encapsula la petición HTTP, la validación de la respuesta y el manejo de errores del contrato descrito en la sección 6. Las pruebas de página y de servicio mockean la API; no deben llamar al servicio remoto.
- Usar el sistema centralizado de diseño: clases `ui-*` y variables semánticas de `src/design/tokens.css` y `src/design/components.css`. Tailwind puede utilizarse para layout, espaciado y responsive.
- Mantener compatibilidad con los temas claro y oscuro; no definir colores de marca directamente en el JSX ni en una hoja local.
- Usar `lucide-react` para los iconos, con nombres accesibles en los controles que no tengan texto visible.
- Centralizar todo texto estático en las traducciones existentes de Català (`ca`), Español (`es`) e English (`en`).
- Asegurar navegación por teclado, foco visible, etiquetas para el campo, anuncios accesibles del estado de espera y mensajes de error asociados al chat.
- Tratar el contenido de la respuesta como texto no confiable: no ejecutar HTML ni contenido activo recibido de la API.

## 8. Pruebas de aceptación

- El usuario puede escribir y enviar una pregunta válida; ésta aparece en el historial.
- La ruta `/agent-company` muestra la página dentro del `AppShell`, y **Consulta de empresa** aparece en la posición indicada y se marca activa al navegar.
- La interfaz muestra el estado de espera hasta recibir la respuesta.
- Una respuesta válida de la API aparece asociada al rol de agente y en el orden correcto.
- Un fallo de API no elimina la pregunta ni los mensajes previos; el error y la opción de reintento se muestran según corresponda.
- No se envían preguntas vacías ni se duplica accidentalmente una petición por doble clic.
- Se validan el formato de petición y respuesta con mocks del servicio, sin depender de la API real en las pruebas unitarias.
- La API acepta el token de sesión en `Authorization`, conserva la clave pública/anon como `apikey` en las consultas de datos y permite que RLS limite los resultados de la sesión invitada. Las pruebas de integración del backend deben cubrir un token anónimo válido, token ausente/caducado y errores de consulta; no usar `service_role`.
- Los estados inicial, cargando, respuesta, error y sin respuesta válida funcionan en los tres idiomas y en ambos temas.
- El diseño sigue siendo usable en móvil con teclado virtual, y los controles son accesibles por teclado.

## 9. Fuera del alcance inicial

El contrato de API, la ruta `/agent-company`, la etiqueta de navegación **Consulta de empresa**, el título y la descripción de la página están definidos e implementados. Queda fuera de esta entrega:

- **Auditoría:** `chat_logs` aún no existe en Supabase. Su creación, funcionamiento, retención y controles de acceso se revisarán más adelante; la interfaz no presupone que se guarden las consultas.

El alcance inicial no incluye persistencia de historial en el frontend, sugerencias iniciales, botón de nueva conversación, solicitudes concurrentes ni formato Markdown enriquecido.
