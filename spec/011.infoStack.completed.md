# Especificación: 011 - Información: Stack Tecnológico

## 1. Objetivo

Crear una página informativa que explique, de forma visual y fácil de consultar, las tecnologías, servicios y decisiones de arquitectura que componen WaveCore. La página es documentación visible dentro de la aplicación; no consulta datos de Supabase ni muestra métricas operativas.

## 2. Navegación y estructura

- Añadir al final de los elementos de navegación del menú lateral una sección **Información**, después de las secciones y páginas existentes.
- La sección contiene el elemento **Stack Tecnológico**, que abre `/feature/stack_info`.
- Reubicar el acceso existente **Stack Tecnológico** de la sección **Finanzas** para evitar entradas duplicadas. La ruta nueva es el destino canónico; `/stack` debe seguir funcionando redirigiendo a `/feature/stack_info`.
- Implementar la página en `src/features/stack_info/`, dentro del shell común.
- La sección Información es una etiqueta de agrupación, no un enlace. Mantener su ubicación al final del área desplazable de navegación y antes del pie fijo del menú.

## 3. Contenido del stack

Presentar la información agrupada por capas. Cada tecnología debe tener su nombre y, cuando sea útil, una breve explicación de su función en WaveCore.

### Entorno de desarrollo

- **Visual Studio Code** — entorno de desarrollo.
- **GitHub Copilot** — asistente de IA para el desarrollo.

### Frontend

- **React** — librería de interfaz de usuario.
- **TypeScript** — lenguaje de programación.
- **Vite** — herramienta de desarrollo y empaquetado.
- **Vitest** — framework de pruebas.
- **Vercel** — alojamiento del frontend.

### Control de versiones

- **Git** — control de versiones.
- **GitHub** — alojamiento del repositorio y colaboración.

### Base de datos y documentos

- **Supabase** — plataforma de backend y almacenamiento.
- **PostgreSQL** — base de datos relacional utilizada mediante Supabase.
- **Supabase Storage** — almacenamiento de documentos.

### Backend 1: agente de consultas a Supabase

- **Función:** responder consultas sobre las tablas de Supabase.
- **Framework y ejecución:** Node.js, como API independiente.
- **Lenguaje:** JavaScript.
- **Servicio de IA:** Google Gemini API. El backend obtiene los datos necesarios de Supabase, los envía a Gemini para su razonamiento y devuelve una respuesta.
- **Alojamiento:** Vercel, en un proyecto separado del frontend.

### Backend 2: documentos y agente de datos

- **Funciones:** ingerir documentos PDF, dividirlos en chunks y almacenarlos en Supabase; responder consultas sobre los chunks y las tablas.
- **Framework:** FastAPI.
- **Lenguaje:** Python.
- **Servicio de IA:** Google Gemini API. El backend obtiene los datos necesarios de Supabase, los envía a Gemini para su razonamiento y devuelve una respuesta.
- **Alojamiento:** Render.
- **Automatización:** GitHub Actions mantiene activo el servicio de Render según la configuración del proyecto.
- **Objetivo:** proporcionar un agente de datos aumentado con herramientas (*tool-augmented data agent*) que disponga del esquema y contexto de la base de datos para responder consultas.

### Arquitectura

- **Feature-driven**, organizada por características, con inspiración en **Clean Architecture**.
- Explicar brevemente que la organización por features mantiene juntas las partes de cada funcionalidad y separa responsabilidades; no presentarla como una implementación estricta de Clean Architecture si el código no lo es.

## 4. Presentación visual

- Abrir con una cabecera clara, con icono, título **Stack Tecnológico** y una descripción breve de la página.
- Organizar las capas en secciones visualmente diferenciadas y fáciles de recorrer. Usar tarjetas o un patrón equivalente moderno, con jerarquía clara entre nombre de tecnología, función y detalles.
- Dar un tratamiento visual reconocible a los dos backends para que se entiendan sus responsabilidades independientes y su relación con Supabase.
- Incluir los logos oficiales de las tecnologías cuando estén disponibles en los recursos existentes del proyecto. Preferir recursos locales o una dependencia de iconos ya disponible; no depender de imágenes remotas que puedan dejar de cargar. Si no hay un logo apropiado, usar un icono coherente o las iniciales de la tecnología.
- Mantener el nombre de cada tecnología como texto visible junto al logo; el logo no debe ser el único medio para identificarla. Usar texto alternativo adecuado cuando el logo aporte información y tratarlo como decorativo cuando el nombre adyacente ya lo identifique.
- No inventar versiones, servicios, integraciones ni capacidades que no estén enumerados en esta especificación o confirmados por la configuración del proyecto.

## 5. Diseño, accesibilidad e internacionalización

- Seguir la jerarquía visual de Inicio y Dashboard Ventas, ocupar el ancho disponible dentro de `AppShell` y diseñar primero para móvil, sin desbordamiento horizontal.
- Usar el sistema centralizado de diseño (`ui-*`, tokens semánticos y patrones compartidos); no definir paletas o estilos locales por tecnología.
- Mantener contraste y legibilidad en temas claro y oscuro. Los logos deben conservar su legibilidad en ambos temas.
- Toda la interfaz, incluidas descripciones, nombres de secciones, textos accesibles y fallbacks, debe estar traducida a catalán (`ca`), español (`es`) e inglés (`en`). No escribir textos visibles estáticos directamente en el componente.
- Usar estructura semántica, encabezados en orden, foco visible y nombres accesibles para cualquier control interactivo. La página es informativa y no necesita filtros ni acciones de datos.
- Respetar `prefers-reduced-motion`; cualquier animación debe ser discreta y no necesaria para comprender la información.

## 6. Criterios de aceptación

- **Información** aparece como la última sección de navegación y contiene un único acceso **Stack Tecnológico** a `/feature/stack_info`.
- El acceso anterior bajo **Finanzas** deja de aparecer duplicado y `/stack` redirige a la ruta nueva.
- La página muestra todas las tecnologías, funciones, servicios y detalles de arquitectura descritos en esta especificación, agrupados por capa y sin añadir datos no confirmados.
- Los logos aparecen cuando hay recursos adecuados; cada tecnología sigue identificándose claramente por su nombre incluso si no hay logo.
- La página funciona en móvil y escritorio, en temas claro y oscuro, dentro del shell común y sin desplazamiento horizontal.
- Todos los textos visibles y accesibles están traducidos a `ca`, `es` y `en`.
- Las pruebas verifican la ruta, la navegación y la presentación de los grupos y contenidos principales, sin necesidad de conectar Supabase ni servicios externos.
