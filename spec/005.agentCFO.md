# Especificación 005: Agente CFO - Repositorio documental

## 1. Objetivo y arquitectura

Implementar en la aplicación frontend existente (React, Vite y TypeScript) el módulo de documentos corporativos para subir archivos PDF y consultar los documentos indexados por la API.

* **Ubicación de la funcionalidad**: `src/features/agent_cfo/`.
* Mantener vistas, componentes y acceso a la API organizados dentro de esta feature, siguiendo los patrones ya presentes en el proyecto.
* Tipar estrictamente los metadatos, los formularios y las respuestas de la API.
* Reutilizar el sistema de diseño centralizado y las traducciones en catalán, español e inglés. No añadir textos estáticos de UI directamente en los componentes.

## 2. Navegación

En el menú principal:

1. Mantener la sección **Finanzas** y sus elementos actuales.
2. Añadir la sección **Documentación** inmediatamente después de **Finanzas**.
3. Añadir bajo ella el elemento **Repositorio**, que abre la vista de gestión, subida y listado de documentos PDF.

La ruta propuesta para la página es `/agent-cfo`.

## 3. Repositorio de documentos

La página tendrá en la parte superior un botón **Subir documento** que permitirá abrir el formulario de ingesta. Debajo se mostrará el listado de documentos subidos, leído directamente desde la tabla `documentos` de Supabase. La página debe mostrar estados explícitos de carga, error y ausencia de documentos. No presentar errores como resultados vacíos o valores válidos.

### Flujo implementado actualmente en el backend

La API FastAPI registra `POST /api/documents/ingest` y procesa la solicitud en este orden:

1. Comprueba que el tipo MIME declarado por el cliente sea `application/pdf`.
2. Lee el archivo completo en memoria y extrae el texto por página con PyMuPDF; un PDF inválido produce HTTP `422`.
3. Sube el PDF al bucket privado `waveStorageTest` de Supabase Storage, bajo una ruta `CFO_PDFs/<uuid>.pdf`.
4. Genera embeddings de los fragmentos con Gemini.
5. Inserta los metadatos en `documentos` y los fragmentos/embeddings en `document_chunks`.
6. Responde con HTTP `201` y un objeto que contiene `id_documento` y `url_storage`. `url_storage` es la ruta interna del objeto en Storage, no una URL pública para abrir directamente.

Los errores observados en el endpoint incluyen HTTP `415` cuando el MIME recibido no es `application/pdf` y HTTP `422` cuando PyMuPDF no puede procesar el archivo como PDF válido.

El endpoint no implementa actualmente autenticación/autorización ni límite de tamaño del archivo. La comprobación del MIME no prueba por sí sola que el contenido sea PDF. El procesamiento consta de varias escrituras separadas y no tiene una transacción común; un error en una etapa posterior puede dejar recursos parciales. La UI no debe asumir que toda respuesta de error implica que no se guardó ningún recurso ni realizar reintentos automáticos de la ingesta.

El flujo anterior describe el comportamiento actual para integrar el frontend; no implica que sus controles sean suficientes para producción. Antes de exponer la API públicamente, implementar autenticación/autorización, límite de tamaño también en backend, validación fiable del contenido y tratamiento/compensación de fallos parciales.

La tabla que utiliza el listado tiene este esquema:

```sql
CREATE TABLE documentos (
    id_documento VARCHAR(50) PRIMARY KEY,
    titulo VARCHAR(255) NOT NULL,
    tipo_documento VARCHAR(100) NOT NULL,
    departamento_origen VARCHAR(100) NOT NULL,
    fecha_emision DATE NOT NULL,
    resumen_ejecutivo TEXT,
    url_storage VARCHAR(500) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

El listado debe consultar Supabase usando el cliente ya inicializado en la aplicación y la sesión disponible, sujeto a los permisos y políticas RLS de la tabla. No se debe utilizar ni exponer la clave `SUPABASE_SERVICE_ROLE_KEY` en el frontend. El backend debe insertar el registro en `documentos` como parte del proceso de ingesta para que el listado refleje los documentos subidos.

### 3.1 Ingesta de documentos

Enviar la petición `POST /api/documents/ingest` como `multipart/form-data`. El contrato confirmado por la documentación de la API local es:

| Campo | Tipo | Requerido | Reglas |
|---|---|---:|---|
| `file` | Archivo binario | Sí | PDF; el frontend rechazará archivos mayores de 10 MB (10.000.000 bytes). La API actual no aplica límite de tamaño, por lo que ese límite también debe implementarse en backend antes de producción. |
| `titulo` | `string` | Sí | Título descriptivo del documento. |
| `tipo_documento` | `string` | Sí | Ejemplos: Balance, Factura, Memoria Anual, Informe de Gestión. |
| `departamento_origen` | `string` | Sí | Ejemplos: Finanzas, Contabilidad, Control de Gestión. |
| `fecha_emision` | `string` (`date`) | Sí | Fecha en formato `YYYY-MM-DD`. |
| `resumen_ejecutivo` | `string` o `null` | No | Texto descriptivo o notas del documento. |

El selector de tipo y departamento puede ofrecer los ejemplos anteriores hasta que la API proporcione catálogos. No asumir que la lista es exhaustiva.

La interfaz debe validar campos obligatorios, extensión PDF y tamaño máximo de 10 MB (10.000.000 bytes) antes del envío, y comunicar los errores de validación y de API de forma visible y traducida. El formulario envía el MIME `application/pdf`; la API actual comprueba ese MIME y el parser puede rechazar un PDF inválido con `422`. La API todavía no comprueba el límite de 10 MB ni autentica o autoriza la petición; la validación del navegador no es una medida de seguridad y esos controles deben añadirse al backend antes de producción. La respuesta exitosa esperada es HTTP `201` con `id_documento` y `url_storage`.

La referencia disponible al endpoint durante el desarrollo es [Ingest Document en la documentación local de FastAPI](http://127.0.0.1:8000/docs#/documents/ingest_document_api_documents_ingest_post).

### 3.2 Listado

No existe actualmente un endpoint de consulta de documentos en la API. Consultar los registros directamente desde `documentos` mediante el cliente Supabase del frontend y mostrar como mínimo:

* Título del documento.
* Tipo de documento y departamento de origen.
* Fecha de emisión.
* Identificador único `id_documento`.
* Fecha de subida (`created_at`).
* Acción para abrir o descargar el documento, sólo cuando se haya implementado acceso compatible con el bucket privado.

Ordenar inicialmente por `created_at` descendente. La tabla no define una columna de estado de indexación; no mostrar un estado. Después de una respuesta HTTP `201`, refrescar el listado desde Supabase. La escritura de `documentos` la realiza actualmente el backend con la clave `service_role`; el frontend sólo lee con el cliente público existente.

Antes de habilitar esta lectura, configurar y probar permisos `SELECT` y políticas RLS apropiadas para la clave pública y las sesiones de la aplicación. No desactivar RLS ni usar credenciales privilegiadas en el cliente. El bucket actual es privado y `url_storage` contiene sólo una ruta; para abrir/descargar archivos hace falta definir e implementar una vía autorizada, como URLs firmadas emitidas por el backend. Hasta entonces, el listado no debe presentar `url_storage` como enlace navegable.

## 4. Conectividad y configuración por entorno

El desarrollo inicial utilizará la API local, accesible en `http://127.0.0.1:8000`. Más adelante se publicará la API en Render.

* La URL base se configurará mediante una variable no secreta del frontend, por ejemplo `VITE_API_BASE_URL`.
* El destino debe poder cambiarse mediante la configuración del entorno, sin cambios de código: URL local durante el desarrollo y URL pública de Render cuando se despliegue la aplicación.
* No fijar la URL de la API en los componentes. Centralizar la construcción de peticiones en el cliente de API de la feature.
* La aplicación debe fallar de forma explícita y mostrar un error útil si la URL base no está configurada o la API no está disponible.
* En la configuración actual el backend permite CORS desde cualquier origen (`*`) para desarrollo. Antes de producción, restringir `allow_origins` a los dominios del frontend; CORS no sustituye autenticación.
* La URL local de FastAPI no debe usarse como destino de producción.

Ejemplo de configuración local del frontend:

```env
VITE_API_BASE_URL=http://127.0.0.1:8000
```

En producción, configurar `VITE_API_BASE_URL` con la URL pública asignada al servicio de Render. Esta variable puede estar expuesta al navegador; no debe contener secretos.

## 5. Autenticación y secretos del backend

La API actual no implementa autenticación ni autorización para la ingesta: el endpoint recibe la solicitud sin validar una sesión o token. Antes de producción, definir e implementar el mecanismo de autenticación/autorización entre frontend y backend. La lectura directa del listado desde Supabase usa el cliente ya inicializado en el frontend y debe quedar limitada por políticas RLS y permisos `SELECT` de la tabla. El frontend no debe incluir credenciales privilegiadas en las peticiones ni usar la clave `service_role`.

La API necesita las siguientes variables de entorno del lado del servidor:

```env
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=
GEMINI_API_KEY=
```

* En local, la configuración actual carga estas credenciales desde `.env` en la raíz del repositorio del backend; ese archivo no se debe versionar. En Render, usar el mecanismo seguro de variables de entorno del servicio.
* No incluirlas en archivos del frontend, en variables `VITE_*`, en el repositorio, en logs ni en respuestas de la API.
* En el frontend se configuran la URL base pública de la API y las credenciales públicas de Supabase que ya requiere el cliente existente (`VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY`). Las variables con prefijo `VITE_` forman parte del código accesible al navegador; nunca deben contener secretos.
* Si se documentan nombres de variables en plantillas de configuración versionadas, usar valores vacíos o marcadores, nunca secretos reales.

## 6. Criterios de aceptación

* El elemento **Repositorio** aparece bajo **Documentación**, inmediatamente después de **Finanzas**, y lleva a `/agent-cfo`.
* La página permite completar y enviar el formulario con el contrato multipart descrito; el frontend rechaza archivos que no sean PDF o superen 10 MB.
* La página informa claramente de los estados de carga, éxito y error de la ingesta. En éxito reconoce HTTP `201` y recibe `id_documento` y `url_storage`.
* La parte superior de la página ofrece el botón **Subir documento** y el listado inferior carga sus registros directamente de `documentos` en Supabase.
* El listado distingue carga, error y ausencia de datos. Sólo permite abrir/descargar archivos cuando exista un mecanismo de acceso autorizado al bucket privado.
* Cambiar entre la API local y la API desplegada en Render requiere sólo cambiar la configuración de `VITE_API_BASE_URL`.
* Antes de producción, el backend aplica autenticación/autorización, límite de 10 MB y CORS restringido, y se ha probado el acceso RLS del listado y el acceso autorizado a Storage.
* Los textos de interfaz y accesibilidad están traducidos en `ca`, `es` y `en`; la página es responsive y compatible con los temas claro y oscuro.
* Las pruebas cubren validación del formulario, envío multipart, errores de API y estados del listado, mockeando tanto la API como las consultas a Supabase.
